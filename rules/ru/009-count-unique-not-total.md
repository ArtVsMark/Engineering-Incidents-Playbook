# Считайте уникальные имена, а не записи

**Область.** метрики

**Правило.** Счётчик, суммирующий записи об одном объекте, врёт при повторах.
Сначала сверните по идентификатору.

## Инцидент

Витрина утверждала «32 проверки на PR». Реальность — шестнадцать.

```
PR #1294: 16 записей, 16 уникальных имён, дублей нет
PR #1293: 32 записи, 16 уникальных имён, дубли: coverage-combine,
          test (windows-latest, 3.14, true), test (macos-latest, 3.12, false)…
```

После обновления ветки GitHub создаёт **второй комплект** check-runs, а первый
остаётся висеть на коммите. `total_count` складывает оба.

Разница между двумя PR — только в том, обновляли ли ветку. Никакой поломки:
API отдаёт ровно то, что есть.

## Второй случай, тот же корень

Тот же обход считал «плохими» проверки, у которых `conclusion` пустой, — и
записал в них семь **выполняющихся**. Едва не поднял ложную тревогу о красном
CI.

Причина того же класса: поле означало не то, что предполагалось. Пустой
`conclusion` — это «ещё идёт», а не «провалилась».

## Почему

API отдаёт историю событий, а не текущее состояние. Записей о проверке столько,
сколько раз она запускалась; «сколько проверок у этого PR» — это вопрос об
**уникальных именах**, а не о числе записей.

Ошибка тихая: цифра правдоподобна, никто не удивляется, и она живёт до тех пор,
пока её не пересчитает машина.

## Применимость

**Работает** для любых счётчиков поверх журналов событий: прогоны, попытки
доставки, ретраи, вебхуки.

Обобщение: **прежде чем считать, спросите — что именно является единицей?**
Событие или объект? Ответ определяет, нужна ли свёртка по ключу.

**Не работает** там, где повторы значимы сами по себе: число попыток,
количество ретраев — там как раз нужны все записи.
