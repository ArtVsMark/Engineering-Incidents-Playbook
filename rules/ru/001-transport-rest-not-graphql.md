# Транспорт к GitHub: REST по умолчанию, GraphQL только там, где REST не умеет

**Область.** квоты, API

**Правило.** Все операции с GitHub — по REST. GraphQL применяется, только если
операция в REST физически отсутствует, и каждый такой случай назван поимённо.

## Инцидент

Замер квоты посреди обычной рабочей сессии:

```
core:    used 11   / 5000
graphql: used 2669 / 5000
```

2669 points — это примерно **девять операций**: одна GraphQL-операция стоит
~300 points. За те же девять обращений REST списал бы 9 запросов из 5000.

Больше половины часового бюджета ушло на работу, целиком доступную в REST, —
просто вызванную не тем инструментом.

Позже в тот же день счётчик показал `used: 10435` при лимите 5000: механизм
продолжал обращаться после исчерпания и получать 403. Работа встала на час.

## Почему

Разница не в удобстве, а в **вместимости**: 300 против 1. Конвейер, который по
REST укладывается в проценты квоты, по GraphQL физически не помещается в час.

«Экономия на числе запросов» оправданием не служит: GraphQL выигрывает, только
если заменяет больше 300 REST-запросов за раз, а в рутине по issue и PR такого
не бывает.

Отдельная ловушка: `used` считает **попытки, а не успехи**. Сверх лимита запрос
отбивается 403 и всё равно списывается — «добить остаток» не выйдет.

## Применимость

**Работает:** любой автоматизированный конвейер поверх GitHub API, особенно с
несколькими агентами на одном аккаунте — квота общая.

**Не работает:** там, где нужны операции без REST-эквивалента. Их немного, и
список закрытый: включение авто-мержа (`enablePullRequestAutoMerge`),
Projects V2, Discussions, минимизация комментария.

**Неприменимо** вне GitHub: у других хостингов другая тарификация.
