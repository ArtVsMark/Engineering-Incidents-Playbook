# Обязательную проверку удовлетворяет любая запись с её именем, включая пропущенную

**Область.** конвейер,надёжность

**Ступень.** 2 — конвейер и CI

**Правило.** Защита ветки сверяет ИМЯ записи проверки, а не её исход:
нейтральная — пропущенная — засчитывается наравне с успешной. Поэтому на одной
голове не должно оставаться больше одной живой записи с именем обязательной
проверки. Механизм, который «просто не делает работу» на части событий, запись
всё равно создаёт: условие у работы вычисляется ПОСЛЕ её создания. Такой
механизм обязан либо не порождать событие вовсе, либо носить другое имя, либо
вытеснять предыдущую запись отменой — отменённая слияние держит, пропущенная
нет.

**Переносится вне Claude Code.** частично — правило про поведение защиты ветки
у площадки; на площадке с другой семантикой обязательных проверок предмет
исчезает, но вопрос «что засчитывается за выполненное требование» остаётся
везде, где требование проверяется по имени.

## Инцидент

Витрина профиля, 7 сентября 2026. Изменение #140 слилось при КРАСНОЙ
обязательной проверке. Красный прогон завершился в 09:30:32, слияние прошло в
09:52:14 — через двадцать две минуты, то есть не по гонке событий.

На голове лежали ТРИ записи с именем `PR check`: `failure`, `skipped` и
`cancelled`. Защита ветки сочла требование выполненным.

Обе половины были осознанными починками прошлых инцидентов, и каждая по
отдельности верна:

- условие `if` у работы завели, чтобы прогон не будился на метку конвейера —
  она не меняет классификацию, и гонять из-за неё сборку незачем;
- отдельную группу параллелизма завели ровно затем, чтобы события меток НЕ
  отменяли настоящую проверку: до этого из восьми прогонов шесть отменялись
  (#100, #103).

Вместе они отключили обязательную проверку целиком: пропуск по условию оставлял
запись `skipped`, а разведённые группы позволяли записям копиться рядом вместо
того, чтобы вытеснять друг друга.

Заметить это можно было только сверкой времён — список проверок выглядел
обычной россыпью крестиков.

## Почему

Условие у работы (`if`) не отменяет её появления в списке проверок: площадка
создаёт работу, вычисляет условие и оставляет запись со статусом «пропущено».
Для защиты ветки «пропущено» — не отсутствие ответа, а нейтральный ответ, и
нейтральный она принимает.

Отсюда асимметрия, которая и делает дефект незаметным: ОТМЕНА держит слияние, а
ПРОПУСК его отпускает. Две операции, выглядящие одинаково безобидно —
«прогон не понадобился», — расходятся ровно в том, что важно.

Опасность накапливается сложением. Каждая половина по отдельности — уборка
шума, и каждая обоснована своим замером. Проверять надо не половину, а
результат: сколько живых записей с именем обязательной проверки остаётся на
голове.

## Практические границы

- на голове остаётся ОДНА живая запись с именем обязательной проверки;
- работе, которую хочется пропускать по условию, дают другое имя либо не
  запускают её событием вовсе — фильтром событий, а не условием внутри;
- группа параллелизма заводится так, чтобы новая запись вытесняла прежнюю
  отменой, а не ложилась рядом;
- необязательный канал этому правилу не подчиняется — но, делая его
  обязательным, условие у работы снимают первым.

## Применимость

**Работает** там, где слияние держит проверка по ИМЕНИ: защита ветки GitHub,
любая система, где требование задано названием, а не исходом.

**Не работает** там, где требование задано исходом конкретного прогона либо
слияние держит человек. Не работает и для необязательных каналов: их запись
слияние не держит ни в каком статусе, и число записей там безразлично.

**Признак нарушения:** на одной голове больше одной записи с именем
обязательной проверки, и хотя бы одна из них — `skipped`.
