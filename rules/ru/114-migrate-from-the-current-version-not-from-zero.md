# Миграция идёт от текущей версии, а не от нуля

**Область.** данные, миграции

**Правило.** Каждая ступень применяется **только** к состоянию, которое её не
проходило. Безусловный прогон всех ступеней ломает уже мигрированное, а «версия
выше ожидаемой» — не ошибка, а норма для новой базы.

## Инцидент

Хранилище дошло до третьей версии схемы. Ступени применялись подряд, начиная с
первой.

Примитив, применяющий ступень, знает только про **свою** версию и считает любую
версию выше запрошенной откатом. На базе второй версии — а такими были все базы,
созданные до этого изменения, — безусловный вызов первой ступени бросал ошибку
«схема новее ожидаемой», и история отваливалась **сразу после обновления
продукта**.

То есть дефект срабатывал ровно у тех, у кого данные уже накопились, и ровно в
момент обновления. Поймано тестом миграции со второй версии на третью — то есть
тестом **перехода**, а не тестом создания с нуля.

Второй урок из того же места — **порядок относительно наполнения**. Ступень,
меняющая структуру, идёт до заполнения производных данных: заполнение пишет
через код, который уже знает про новые поля. Обратный порядок даёт наполовину
заполненный агрегат.

Третий — про инструмент: применение схемы идёт через функцию, не делающую
неявного подтверждения транзакции. Обычный способ выполнить пакет команд снял бы
взятую выше блокировку записи.

## Почему

Миграция — это функция от **текущего** состояния, а не сценарий с начала. Код,
написанный как «применим всё по очереди», верен ровно один раз — при создании с
нуля, то есть в том единственном случае, который разработчик и проверяет чаще
всего.

Отсюда несимметричность риска: путь «с нуля» проверяется каждым запуском тестов,
путь «со второй на третью» — только специальным тестом, которого обычно нет. А
пользователи ходят именно вторым путём.

Второе: **«версия выше ожидаемой» — не ошибка**. Для примитива это откат, для
мигратора — нормальная ситуация «ступень уже пройдена». Смешение этих двух
взглядов и даёт отказ на ровном месте.

## Практические границы

- перед каждой ступенью — проверка текущей версии; ступени не применяются
  безусловно;
- тесты покрывают **переходы**, а не только создание с нуля: с каждой живой
  версии на текущую;
- порядок ступеней относительно наполнения производных данных зафиксирован и
  объяснён;
- миграция идёт в одной транзакции, и инструменты выбираются так, чтобы не
  снимать блокировку неявно;
- у хранилища записано, какие версии считаются живыми, — иначе список переходов
  растёт бесконечно.

## Применимость

**Работает** для схем баз, форматов файлов, версий настроек, состояний кэша.

**Не работает** там, где старые состояния не поддерживаются и удаляются: тогда
нужен не мигратор, а внятный отказ с инструкцией.

**Признак нарушения:** обновление ломает данные только у давних пользователей.
