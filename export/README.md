# Контракт потребления · Consumption contract

Каталог отдаёт правила машиночитаемо, проект-потребитель отвечает, что он с
каждым правилом сделал. Зачем это нужно и почему устроено именно так —
[правило 129](../rules/ru/129-a-catalogue-needs-a-consumption-contract.md).

The catalogue publishes its rules machine-readably; a consuming project answers
what it did with each of them. Why this exists and why it is shaped this way —
[rule 129](../rules/en/129-a-catalogue-needs-a-consumption-contract.md).

## Что отдаёт каталог · What the catalogue publishes

[`rules.json`](rules.json) — собирается `scripts/build_rules_index.py` из самих
правил и сверяется гейтом: PR, где правило добавлено, а экспорт не пересобран, в
CI красный. Руками не правится.

Generated by `scripts/build_rules_index.py` from the rules themselves and checked
by a gate: a PR that adds a rule without rebuilding the export goes red. Never
edited by hand.

```jsonc
{
  "schema": "1.0",
  "catalogue": "https://github.com/ArtVsMark/claude-code-playbook",
  "count": 130,                       // пример · example value
  "rules": [
    {
      "id": "129",                        // номер, не переиспользуется · never reused
      "slug": "a-catalogue-needs-a-consumption-contract",
      "title": { "ru": "…", "en": "…" },
      "areas": { "ru": ["каталог", "контракты"], "en": ["catalogue", "contracts"] },
      "added": "2026-08-21",              // из истории файла · from file history
      "files": { "ru": "rules/ru/129-….md", "en": "rules/en/129-….md" },
      "trails": [                          // структурно, а не строкой · structured
        { "repo": "ArtVsMark/claude-code-playbook", "issue": "15" }
      ]
    }
  ]
}
```

**Как читать · How to fetch.** Обычным HTTP по «сырой» ссылке на ветку `main`:
ни API площадки, ни клона, ни токена — подключиться может кто угодно, включая
проект, к которому у каталога нет никакого отношения.

Plain HTTP from the raw link on `main`: no platform API, no clone, no token —
anyone can subscribe, including a project the catalogue has nothing to do with.

```
https://raw.githubusercontent.com/ArtVsMark/claude-code-playbook/main/export/rules.json
```

**`trails` бывает пустым, и это значение, а не пробел.** У большинства правил
след ведёт в файл или документ, а не в задачу. Пустой список означает «ссылок на
задачи нет», а не «не разобрали»: неразбираемый след роняет сборку.

**`trails` may be empty, and that is a value rather than a gap.** For most rules
the trail points at a file or a document rather than an issue. An empty list
means "no issue references", never "we failed to parse": an unparseable trail
fails the build.

## Что отдаёт потребитель · What the consumer publishes

`.rules/bindings.json` в своём репозитории — по записи на правило. Заготовка:
[`templates/bindings.json`](../templates/bindings.json).

`.rules/bindings.json` in its own repository, one record per rule. Boilerplate:
[`templates/bindings.json`](../templates/bindings.json).

| Поле · Field | Значения · Values | Обязательно · Required |
|---|---|---|
| `status` | `active` · `rejected` · `not-applicable` · `unreviewed` | всегда · always |
| `mechanism` | `gate` · `process-step` · `none` | при `active` · when `active` |
| `where` | путь к скрипту, шагу конвейера или разделу свода · path to a script, a pipeline step or a section of the rulebook | при `active` · when `active` |
| `why` | причина решения · the reason for the decision | при `rejected` и `not-applicable` |

**Почему файл живёт у потребителя, а не здесь.** Там живёт механизм: одно
правило в проекте с полным конвейером держится гейтом, в витрине — шагом
сборки, в статическом сайте ничем. Каталог про чужие гейты не знает и не
проверяет их — «у нас держится гейтом» это утверждение проекта, и отвечает за
него его же конвейер.

**Why the file lives with the consumer.** Because the mechanism does: the same
rule is held by a CI gate in one project, by a build step in a storefront, by
nothing in a static site. The catalogue does not know about foreign gates and
does not verify them — "held by a gate here" is the project's own claim, and its
own pipeline answers for it.

**Четыре статуса, и три из них не взаимозаменяемы.** `rejected` — предмет есть,
решение иное. `not-applicable` — предмета нет. `unreviewed` — ещё не смотрели.
Именно третий и есть настоящая потеря, и склеивать его с первыми двумя нельзя:
ради этого различия контракт и заводится.

**Four statuses, and three of them are not interchangeable.** `rejected` — the
subject exists, the decision differs. `not-applicable` — there is no subject.
`unreviewed` — nobody has looked yet. The third is the real loss, and merging it
into the first two is exactly what this contract exists to prevent.

## Как схема меняется · How the schema evolves

Правила эволюции записаны здесь же, рядом со схемой — иначе их не прочитает тот,
кто читает схему ([113](../rules/ru/113-a-contract-states-how-it-may-change.md)).

- **Версия `MAJOR.MINOR`.** MINOR — совместимое изменение: добавлено поле,
  расширен список значений. MAJOR — несовместимое: поле удалено, переименовано
  или сменило смысл.
- **Читатель игнорирует незнакомые поля.** Это условие, при котором MINOR
  безопасен; читатель, падающий на новом поле, ломается по своей вине.
- **Обязательные поля задним числом не добавляются.** Новое поле необязательно
  до следующего MAJOR.
- **Миграция идёт от текущей версии, а не от нуля**
  ([114](../rules/ru/114-migrate-from-the-current-version-not-from-zero.md)):
  потребитель, отставший на две версии, поднимается по шагам.
- **Переходная заглушка получает срок**, иначе она навсегда
  ([094](../rules/ru/094-a-compatibility-shim-makes-migration-permanent.md)).

Rules of evolution live next to the schema, or whoever reads the schema will not
read them. `MAJOR.MINOR`: MINOR is a compatible change (a field added, a value
list widened), MAJOR is not (a field removed, renamed or repurposed). Readers
ignore unknown fields — that is the condition under which MINOR is safe.
Mandatory fields are never added retroactively. Migration goes from the current
version, not from zero. A transitional shim gets an expiry date.

**Сломать формат — значит сломать чужие проекты**, в том числе те, о которых
здесь никто не знает. Поэтому версия есть с первого дня, а не с того, когда
«понадобится».

**Breaking the format means breaking other people's projects**, including ones
nobody here knows about. Hence a version from day one rather than from the day it
seems needed.

## Отвергнутые варианты · Rejected alternatives

Записаны, чтобы их не переоткрывали
([042](../rules/ru/042-decision-records-its-alternatives.md)).

| Вариант · Option | Почему нет · Why not |
|---|---|
| Рассылка из каталога через API площадки · Pushing from the catalogue over the platform API | Нужен токен с правом писать во все проекты, включая приватные. Одна точка отказа и широкие права ради уведомления · A token that can write into every project, including private ones: one point of failure and broad rights for the sake of a notification |
| Копия скрипта в каждом проекте · A copy of the script in every project | Стеки разные, копии разъедутся с первой правки · Different stacks; the copies drift from the first edit ([090](../rules/ru/090-shared-helpers-move-up-not-sideways.md)) |
| Экспорт отдельной веткой · Publishing the export on a separate branch | Потребовал бы прав на запись и отдельного конвейера. Экспорт лежит в `main` рядом со значками и держится тем же гейтом · Would need write permissions and a pipeline of its own; the export sits in `main` next to the badges and is held by the same gate |
| Хранить `mechanism` в каталоге · Keeping `mechanism` in the catalogue | Одно правило держится в разных проектах по-разному; каталог про чужие гейты не знает · The same rule is held differently in different projects |
| Вести «где действует» руками · Maintaining "where it applies" by hand | Отстанет молча · It will fall behind silently ([049](../rules/ru/049-derive-state-from-live-artifacts.md)) |

## Названный пробел · The named gap

**Приватный участник не агрегируется.** Его `bindings.json` недоступен публично,
и в сводной таблице он читается как «неизвестно», а не «не принято» — разница
существенная ([046](../rules/ru/046-name-the-gaps-do-not-level-them.md)).

**A private participant cannot be aggregated.** Its `bindings.json` is not
publicly readable, so the summary reads "unknown", never "not adopted".

**Ответ чужого проекта — недоверенные данные.** Он попадает в таблицы цитатой, а
не командой: каталог ничего из него не исполняет
([085](../rules/ru/085-content-from-the-subject-is-untrusted-input-to-the-prompt.md)).

**A foreign project's answer is untrusted data.** It enters the tables as a
quotation, never as a command.

## Чего здесь пока нет · Not here yet

Реестр потребителей, сверка и обновление «входящих» у потребителя — следующий
шаг, [#14](https://github.com/ArtVsMark/claude-code-playbook/issues/14).
Подключать нечего, пока нет ни одного потребителя, и пустой реестр объявляется
явно, а не подразумевается ([027](../rules/ru/027-empty-state-is-a-state.md)).

The consumer registry, the diffing and the inbox update are the next step. There
is nothing to connect while there are no consumers, and an empty registry is
declared rather than implied.
