# Контракт потребления · Consumption contract

Каталог отдаёт правила машиночитаемо, проект-потребитель отвечает, что он с
каждым правилом сделал. Зачем это нужно и почему устроено именно так —
[правило 129](../rules/ru/129-a-catalogue-needs-a-consumption-contract.md).

The catalogue publishes its rules machine-readably; a consuming project answers
what it did with each of them. Why this exists and why it is shaped this way —
[rule 129](../rules/en/129-a-catalogue-needs-a-consumption-contract.md).

## Что отдаёт каталог · What the catalogue publishes

[`rules.json`](rules.json) — собирается `scripts/build_rules_index.py` из самих
правил и сверяется гейтом: PR, где правило добавлено, а экспорт не пересобран, в
CI красный. Руками не правится.

Generated by `scripts/build_rules_index.py` from the rules themselves and checked
by a gate: a PR that adds a rule without rebuilding the export goes red. Never
edited by hand.

```jsonc
{
  "schema": "1.1",
  "catalogue": "https://github.com/ArtVsMark/claude-code-playbook",
  "count": 130,                       // пример · example value
  "rules": [
    {
      "id": "129",                        // номер, не переиспользуется · never reused
      "slug": "a-catalogue-needs-a-consumption-contract",
      "title": { "ru": "…", "en": "…" },
      "areas": { "ru": ["каталог", "контракты"], "en": ["catalogue", "contracts"] },
      "added": "2026-08-21",              // из истории файла · from file history
      "files": { "ru": "rules/ru/129-….md", "en": "rules/en/129-….md" },
      "trails": [                          // структурно, а не строкой · structured
        { "repo": "ArtVsMark/claude-code-playbook", "issue": "15" }
      ],
      "portable": "partly"                 // ключа может НЕ БЫТЬ · key may be ABSENT
                                           // да · нет · частично → yes · no · partly
    }
  ]
}
```

**Как читать · How to fetch.** Обычным HTTP по «сырой» ссылке на ветку `main`:
ни API площадки, ни клона, ни токена — подключиться может кто угодно, включая
проект, к которому у каталога нет никакого отношения.

Plain HTTP from the raw link on `main`: no platform API, no clone, no token —
anyone can subscribe, including a project the catalogue has nothing to do with.

```
https://raw.githubusercontent.com/ArtVsMark/claude-code-playbook/main/export/rules.json
```

**`portable` — необязательный ключ, и его отсутствие значит «не отвечали».**
Не «не переносится» и не «неизвестно»: у большинства записей поля нет, потому
что вопрос им не задавали, и задним числом он не проставляется. Отбирать по
нему можно только те записи, где ключ есть; остальные — не «нет», а молчание.
README каталога предупреждает «не копируйте целиком, половина заточена под
агентские окна» — этот ключ делает предупреждение выбираемым по записям вместо
общего на весь корпус.

**`portable` is an optional key, and its absence means "we did not answer".**
Not "not portable" and not "unknown": most records have no such field because
the question was never put to them, and it is never filled in retroactively.
Filter on it only among records that carry it; the rest are silence, not "no".

**`trails` бывает пустым, и это значение, а не пробел.** У большинства правил
след ведёт в файл или документ, а не в задачу. Пустой список означает «ссылок на
задачи нет», а не «не разобрали»: неразбираемый след роняет сборку.

**`trails` may be empty, and that is a value rather than a gap.** For most rules
the trail points at a file or a document rather than an issue. An empty list
means "no issue references", never "we failed to parse": an unparseable trail
fails the build.

## Что отдаёт потребитель · What the consumer publishes

`.rules/bindings.json` в своём репозитории — по записи на правило. Заготовка:
[`templates/bindings.json`](../templates/bindings.json).

`.rules/bindings.json` in its own repository, one record per rule. Boilerplate:
[`templates/bindings.json`](../templates/bindings.json).

| Поле · Field | Значения · Values | Обязательно · Required |
|---|---|---|
| `status` | `active` · `rejected` · `not-applicable` · `unreviewed` | всегда · always |
| `mechanism` | `gate` · `process-step` · `none` | при `active` · when `active` |
| `where` | путь к скрипту, шагу конвейера или разделу свода · path to a script, a pipeline step or a section of the rulebook | при `active` · when `active` |
| `why` | причина решения · the reason for the decision | при `rejected` и `not-applicable` |

**Почему файл живёт у потребителя, а не здесь.** Там живёт механизм: одно
правило в проекте с полным конвейером держится гейтом, в витрине — шагом
сборки, в статическом сайте ничем. Каталог про чужие гейты не знает и не
проверяет их — «у нас держится гейтом» это утверждение проекта, и отвечает за
него его же конвейер.

**Why the file lives with the consumer.** Because the mechanism does: the same
rule is held by a CI gate in one project, by a build step in a storefront, by
nothing in a static site. The catalogue does not know about foreign gates and
does not verify them — "held by a gate here" is the project's own claim, and its
own pipeline answers for it.

**Четыре статуса, и три из них не взаимозаменяемы.** `rejected` — предмет есть,
решение иное. `not-applicable` — предмета нет. `unreviewed` — ещё не смотрели.
Именно третий и есть настоящая потеря, и склеивать его с первыми двумя нельзя:
ради этого различия контракт и заводится.

**Four statuses, and three of them are not interchangeable.** `rejected` — the
subject exists, the decision differs. `not-applicable` — there is no subject.
`unreviewed` — nobody has looked yet. The third is the real loss, and merging it
into the first two is exactly what this contract exists to prevent.

## Что отдаёт потребитель наверх · What the consumer sends upstream

`.rules/proposals.json` в своём репозитории — правила, родившиеся **у него** и
предлагаемые каталогу. Адрес называется в реестре, поле `proposals`. Заготовка:
[`templates/proposals.json`](../templates/proposals.json).

`.rules/proposals.json` in its own repository: rules born **there** and offered
to the catalogue. Its address goes in the registry field `proposals`.

| Поле · Field | Что значит · Meaning | Обязательно · Required |
|---|---|---|
| `slug` | короткое имя латиницей, `[a-z0-9-]` · short latin name | всегда · always |
| `claim` | утверждение: что делать и чего не делать · the claim | всегда · always |
| `incident` | что сломалось, с конкретикой · what broke, concretely | всегда · always |
| `trail` | артефакт в этом репозитории, где поломка видна · the artefact where it shows | всегда · always |

**Номера у предложения нет и быть не может.** Его присваивает каталог при
приёме. Не из вкуса: номера не переиспользуются, и если два проекта выберут
номер независимо, столкновение уже нечем починить — ни переименованием, ни
заменой. Единственный канон нумерации — [`rules.json`](rules.json). Поля `id`,
`number`, `rule` в предложении — попытка занять номер снаружи канона, и прогон
о ней скажет.

**A proposal carries no number, and cannot.** The catalogue assigns it on
admission. Numbers are never reused, so two projects choosing independently
produce a collision nothing can repair. `rules.json` is the only canon.

**Потребитель шлёт инцидент, а не готовую запись.** Словарь областей, оба
языковых дерева, ответ о соседях и разрешимый след живут в каталоге; требовать
их от отправителя значило бы разносить туда же и знание о том, как их делать
([090](../rules/ru/090-shared-helpers-move-up-not-sideways.md)).

**The consumer sends an incident, not a finished record.** The area vocabulary,
both language trees, the neighbours answer and a resolvable trail live here.

**Каталог отвечает по каждому предложению** — в `.rules/proposals.json` у себя,
ключ `владелец/репозиторий:слаг`:

| Статус · Status | Что несёт · Carries |
|---|---|
| `admitted` | номер, который присвоил каталог · the number the catalogue assigned |
| `rejected` | причину · the reason |
| `merged-into` | номер существующей записи и причину · the existing rule and why |

Без ответа отправитель не узнаёт исход — ровно та асимметрия, ради которой
заведён `bindings.json` вниз по течению. Держится гейтом
`scripts/collect_proposals.py --check`; опрос — тем же скриптом без ключа, из
`consumers-sync`.

**Тянет каталог, а не толкает потребитель.** Та же причина, по которой рассылка
вниз отвергнута: толчок наверх потребовал бы у потребителя права писать в
каталог. Обычный HTTPS по «сырой» ссылке — ни токена, ни клона, ни прав
([080](../rules/ru/080-every-new-rule-goes-into-the-catalogue.md)).

**The catalogue pulls; the consumer does not push.** A push upstream would need
write rights into the catalogue. Plain HTTPS from a raw link needs none.

## Набор вопросов витрины · The showcase question set

Отдельно от экспорта каталог публикует
[`.rules/showcase.json`](../.rules/showcase.json) — **набор вопросов, на которые
витрина проекта отвечает живым числом**. Он один на все проекты не из
единообразия: разные наборы не сравнить, и то, что проект перестал отвечать, не
заметит никто ([022](../rules/ru/022-one-canonical-document.md)).

У каждого вопроса ровно один ответ: либо `badge` — файл значка, вычисляемый
сборкой и **названный в витрине**, либо `absent` с причиной. Пропуск не
проходит: значка нет и значок застыл с витрины неотличимы, поэтому вопрос без
предмета называется, а не опускается
([046](../rules/ru/046-name-the-gaps-do-not-level-them.md),
[075](../rules/ru/075-a-guard-that-finds-nothing-must-fail.md)).

Держит это `scripts/check_showcase.py`. Потребитель волен взять набор целиком
или ответить `absent` там, где предмета у него нет, — но **ответить обязан на
каждый вопрос**, иначе сравнение теряет смысл.

Alongside the export the catalogue publishes `.rules/showcase.json` — the set of
questions a project's showcase answers with a live number. It is the same set
across projects: differing sets cannot be compared, and nobody notices when a
project stops answering. Each question takes exactly one answer — a `badge`
computed by a build and named in the showcase, or `absent` with a reason. An
omission does not pass: a missing badge and a frozen badge look identical from
the outside.

## Как схема меняется · How the schema evolves

Правила эволюции записаны здесь же, рядом со схемой — иначе их не прочитает тот,
кто читает схему ([113](../rules/ru/113-a-contract-states-how-it-may-change.md)).

- **Версия `MAJOR.MINOR`.** MINOR — совместимое изменение: добавлено поле,
  расширен список значений. MAJOR — несовместимое: поле удалено, переименовано
  или сменило смысл.
- **Читатель игнорирует незнакомые поля.** Это условие, при котором MINOR
  безопасен; читатель, падающий на новом поле, ломается по своей вине.
- **Обязательные поля задним числом не добавляются.** Новое поле необязательно
  до следующего MAJOR.
- **Миграция идёт от текущей версии, а не от нуля**
  ([114](../rules/ru/114-migrate-from-the-current-version-not-from-zero.md)):
  потребитель, отставший на две версии, поднимается по шагам.
- **Переходная заглушка получает срок**, иначе она навсегда
  ([094](../rules/ru/094-a-compatibility-shim-makes-migration-permanent.md)).

Rules of evolution live next to the schema, or whoever reads the schema will not
read them. `MAJOR.MINOR`: MINOR is a compatible change (a field added, a value
list widened), MAJOR is not (a field removed, renamed or repurposed). Readers
ignore unknown fields — that is the condition under which MINOR is safe.
Mandatory fields are never added retroactively. Migration goes from the current
version, not from zero. A transitional shim gets an expiry date.

**Сломать формат — значит сломать чужие проекты**, в том числе те, о которых
здесь никто не знает. Поэтому версия есть с первого дня, а не с того, когда
«понадобится».

**Breaking the format means breaking other people's projects**, including ones
nobody here knows about. Hence a version from day one rather than from the day it
seems needed.

## Отвергнутые варианты · Rejected alternatives

Записаны, чтобы их не переоткрывали
([042](../rules/ru/042-decision-records-its-alternatives.md)).

| Вариант · Option | Почему нет · Why not |
|---|---|
| Рассылка из каталога через API площадки · Pushing from the catalogue over the platform API | Нужен токен с правом писать во все проекты, включая приватные. Одна точка отказа и широкие права ради уведомления · A token that can write into every project, including private ones: one point of failure and broad rights for the sake of a notification |
| Копия скрипта в каждом проекте · A copy of the script in every project | Стеки разные, копии разъедутся с первой правки · Different stacks; the copies drift from the first edit ([090](../rules/ru/090-shared-helpers-move-up-not-sideways.md)) |
| Экспорт отдельной веткой · Publishing the export on a separate branch | Потребовал бы прав на запись и отдельного конвейера. Экспорт лежит в `main` рядом со значками и держится тем же гейтом · Would need write permissions and a pipeline of its own; the export sits in `main` next to the badges and is held by the same gate |
| Хранить `mechanism` в каталоге · Keeping `mechanism` in the catalogue | Одно правило держится в разных проектах по-разному; каталог про чужие гейты не знает · The same rule is held differently in different projects |
| Вести «где действует» руками · Maintaining "where it applies" by hand | Отстанет молча · It will fall behind silently ([049](../rules/ru/049-derive-state-from-live-artifacts.md)) |

## Названный пробел · The named gap

**Приватный участник не агрегируется.** Его `bindings.json` недоступен публично,
и в сводной таблице он читается как «неизвестно», а не «не принято» — разница
существенная ([046](../rules/ru/046-name-the-gaps-do-not-level-them.md)).

**A private participant cannot be aggregated.** Its `bindings.json` is not
publicly readable, so the summary reads "unknown", never "not adopted".

**Ответ чужого проекта — недоверенные данные.** Он попадает в таблицы цитатой, а
не командой: каталог ничего из него не исполняет
([085](../rules/ru/085-content-from-the-subject-is-untrusted-input-to-the-prompt.md)).

**A foreign project's answer is untrusted data.** It enters the tables as a
quotation, never as a command.

## Реестр потребителей · The consumer registry

[`.rules/consumers.json`](../.rules/consumers.json) — проекты, с которыми
каталог связан. Список закрытый и разрешительный: он же решает, что считается
репозиторием в разделе «След» правила, и что попадает в сводную таблицу.

| Поле · Field | Что значит · Meaning |
|---|---|
| `repo` | `владелец/репозиторий` · `owner/repo` |
| `role` | чем проект приходится каталогу · how the project relates to the catalogue |
| `bindings` | адрес ответа: путь внутри каталога или обычная HTTPS-ссылка; `null` — не подключён · path or plain HTTPS link to the answer; `null` means not connected |
| `access` | `public` · `private` — приватный не агрегируется и читается как «неизвестно» · a private one is not aggregated and reads as "unknown" |

## Как подключиться · How to connect

Один рабочий процесс на стороне проекта; своего скрипта заводить не нужно.

One workflow on the project's side; no script of your own.

```yaml
name: rules-inbox
on:
  schedule: [{ cron: "17 6 * * *" }]
  workflow_dispatch:            # ручная кнопка · a manual button (104)
permissions:
  contents: read
  issues: write
jobs:
  inbox:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ArtVsMark/claude-code-playbook@<!--m:ref-->v1.0.0<!--/m:ref-->
        with:
          token: ${{ secrets.GITHUB_TOKEN }}
```

**Пример закреплён тегом, а не веткой — и это не мелочь оформления.** Раньше
здесь стоял `@main`, то есть контракт **показывал** ровно то, от чего
**предостерегает** абзацем ниже. Потребитель копирует пример, а не абзац
([#76](https://github.com/ArtVsMark/claude-code-playbook/issues/76)). Номер в
примере переписывает выпуск, а не человек ([035](../rules/ru/035-version-is-never-edited-by-hand.md));
схема нумерации — [`VERSIONING.md`](../VERSIONING.md). Закрепиться на более
старом релизе законно: это и значит «закрепиться».

**The example pins a tag, not a branch.** It used to show `@main` — the contract
displaying exactly what it warns against one paragraph later. The number is
rewritten by the release, never by hand.

Действие тянет `rules.json`, сверяет со своим `.rules/bindings.json` и ведёт
**одну** задачу-«входящие» со списком нерассмотренных — обновляет ту же, а не
плодит новые. Нерассмотренные правила прогон не роняют: очередь это не поломка.
Красным становится только третий исход — механизм не отработал
([039](../rules/ru/039-three-outcomes-not-two.md)).

The action fetches `rules.json`, diffs it against the project's own
`.rules/bindings.json`, and maintains **one** inbox issue listing what has not
been answered — updating the same issue rather than creating new ones. Pending
rules do not fail the run; only the third outcome does.

Файла `.rules/bindings.json` может ещё не быть — тогда нерассмотрено всё, и
первая же задача-«входящие» об этом и скажет. Отдельного шага «подключение» нет.

## Что каталог отдаёт помимо правил · What else the catalogue publishes

Механизм, а не только текст: гейт, который стоит у нас, подключается
потребителем ссылкой на версию. Логика остаётся в одном месте — копия в третьем
репозитории разъехалась бы с первой правкой
([090](../rules/ru/090-shared-helpers-move-up-not-sideways.md)).

```yaml
- uses: actions/checkout@v4
  with: { fetch-depth: 0 }        # гейту нужна история
- uses: ArtVsMark/claude-code-playbook/.github/actions/attribution@<!--m:ref-->v1.0.0<!--/m:ref-->
  with:
    authors: .github/authors.txt  # СВОЙ список согласованных имён
    baseline: ""                  # свой коммит, с которого спрашивать
```

**Список имён и начало отсчёта принадлежат проекту, а не инструменту.** У
каждого потребителя свои согласованные авторы; подставить чужие — значит
получить красное на верных коммитах, то есть гейт хуже отсутствующего
([051](../rules/ru/051-warn-on-likely-block-on-certain.md)).

**The authors list and the baseline belong to the project, not to the tool.**
Substituting somebody else's turns the gate red on correct commits — worse than
having no gate.

Версию каталога стоит закрепить тегом: подключаться к движущейся ветке значит
получать чужую правку гейта в свой красный прогон.

## Сводная таблица · The summary table

[`where.md`](where.md) и [`where.json`](where.json) собираются
`scripts/aggregate_bindings.py` из ответов потребителей и руками не правятся.
Пустая клетка означает «потребитель не подключён», а не «правило им отклонено» —
это те самые состояния, ради различения которых контракт и заведён.

Объявленный потребитель, чей ответ не читается, — **отказ**, а не пропуск:
иначе «не смогли прочитать» выглядит как «у него всё хорошо»
([075](../rules/ru/075-a-guard-that-finds-nothing-must-fail.md)). Отказ этот
живёт в отдельном прогоне `consumers-sync`, а не в обязательной проверке
изменения: сеть и чужой сервер в обязательном гейте означали бы, что чужая
работа краснеет от сбоя, к которому не имеет отношения. `--check` на изменении
ходит только по диску и отвечает на другой вопрос — «собрано ли то, что
лежит».

Generated by `scripts/aggregate_bindings.py` from the consumers' answers, never
edited by hand. An empty cell means "not connected", not "rejected there". A
declared consumer whose answer cannot be read fails the build rather than being
skipped.

**Чего в механизме нет, и это названо, а не сглажено.** Срок свежести ответа
объявлен в скрипте, но отсчитывать его не от чего: дата последнего чтения жила
бы в производном файле и меняла бы его на каждом прогоне, а отдельный носитель
состояния — это ровно тот ручной реестр, против которого написано
[049](../rules/ru/049-derive-state-from-live-artifacts.md). Пока подключённых
потребителей нет, срок ни на что не влияет; когда появятся — это отдельная
задача, а не строка в этом файле.
