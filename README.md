## Две роли — для внешних и для семьи

**Внешнему проекту каталог раздаёт правила.** Значки и договор фактов — по
желанию, подключение их не требует.

**Для семьи каталог — главный держатель контрактов, её мозг:** все договоры
между проектами, код единого значка и эталон для сверки. Чужих чисел он не
считает — факты о себе каждый проект публикует сам. Цена: сломался каталог —
посерело у всех ([#842](https://github.com/ArtVsMark/Engineering-Incidents-Playbook/issues/842)).

## Зачем это

Свод «делай так» копируют целиком и не соблюдают. Правило держится, пока живо
понимание, **зачем** оно, — а понимание живёт в инциденте, а не в формулировке.

Поэтому здесь не список требований, а каталог разборов. Читаете описание
поломки, узнаёте свою ситуацию — берёте правило вместе с причиной.

## Как пользоваться

**Подключаете проект** — [`CONNECT.md`](CONNECT.md): одна команда собирает
ответ по каждому правилу, канал обратно и ежедневный прогон «входящих».
Механизмы по желанию — действия, проверки, значки, навыки — перечислены там
же, одним списком.

**Начинаете новый проект** — пройдите [`START.md`](START.md): порядок первого
дня и что можно отложить. Заготовки лежат в [`templates/`](templates/) — они
для того, кому инструменты недоступны.

**Ищете решение конкретной боли** — смотрите [`rules/`](rules/README.md): один файл на
правило, вход по номеру или [по областям](rules/README.md#по-областям).

**Не знаете, с чего начать читать** — [`TOP-10.md`](TOP-10.md): десять правил,
которые переносятся дальше своего стека.

**Хотите внести своё** — [`CONTRIBUTING.md`](CONTRIBUTING.md): что здесь
принимают, в каком виде и почему правило без инцидента не принимают.

**Разбираете инцидент в окне Claude Code здесь же** — навыки окна в
[`.claude/skills/`](.claude/skills/README.md): от первичного разбора
(`/incident-triage`) до разбора после починки (`/postmortem`), каждый шаг — по
правилам каталога, а не по памяти.

**Не копируйте каталог целиком.** У каждого правила есть раздел
«Применимость», и в нём честно сказано, **где оно не работает**. Половина
здешнего заточена под агентские окна, GitHub и лимиты; в проекте на другом
стеке это балласт.

## Формат записи

```
Правило        одной фразой
Инцидент       что сломалось, как обнаружили, чем обошлось
Почему         механизм поломки, а не мораль
Применимость   где работает — и где НЕ работает
След           issue или PR, где поломка видна
```

**След обязателен.** Без ссылки на доказательство запись за месяц превращается
в «кто-то говорил, что так лучше».

## Как пополняется

**Правило, родившееся в любом проекте, записывается сюда.** Не выборочно и не
задним числом: в своём проекте остаётся действующая формулировка и ссылка, а
инцидент, доводы и границы применимости живут здесь. Правило без своей истории
через месяц нечем защитить — и в следующий проект оно не переезжает.

Запись делается **в тот же день**. Не «когда-нибудь опишем»: материал портится
быстро. Опыт этого каталога: правила месячной давности приходилось
восстанавливать по документам, потому что в памяти их уже не было.

Полностью — [`080`](rules/ru/080-every-new-rule-goes-into-the-catalogue.md).

## Язык

Каталог ведётся на двух языках, `rules/ru/` и `rules/en/`, с **одинаковыми
именами файлов** — поэтому ссылки между правилами разрешаются одинаково в обоих
деревьях.

Указатель [`rules/README.md`](rules/README.md) — **один на оба языка** и
собирается скриптом из самих файлов. Правило, добавленное только на одном языке,
сборку не проходит: это и есть механизм, не дающий деревьям разойтись. Два
отдельных указателя такого не дают — каждый выглядит полным сам по себе.

## Семья проектов

Проекты семьи обмениваются контрактами, и держит их каталог — см. «Две роли»
выше. У каждого проекта своя роль, и семейный значок показывает, сходится ли
проект с остальными:

| Проект | Роль в семье |
|---|---|
| **Engineering-Incidents-Playbook** (`EIP`, здесь) | правила и их выгрузка, контракт ответа, канал предложений снизу, сводка семьи |
| [Engineering-Pipeline-Mechanisms](https://github.com/ArtVsMark/Engineering-Pipeline-Mechanisms) (`EPM`) | шаги конвейера, которые зовут по адресу с тегом: факты, дрейф, автомерж |
| [ArtVsMark](https://github.com/ArtVsMark/ArtVsMark) (`AVM`) | витрина профиля и договор фактов `facts.json`, по которому каждый проект говорит о себе |
| [Stepik-Python-Grader](https://github.com/ArtVsMark/Stepik-Python-Grader) | потребитель; здесь родилось большинство правил каталога |
| [Glossary-Python](https://github.com/ArtVsMark/Glossary-Python) | потребитель и пара грейдера |
| [Claude-Code_Usage-Token](https://github.com/ArtVsMark/Claude-Code_Usage-Token) | потребитель |

**Семейный значок** — сегменты `gives` (что проект отдаёт), `family` (что берёт
у издателей), `pairs` (парные связи) и `ext` (внешний мир по своим фактам:
плавающая метка исполнителя `…-latest` — красный), справа — блок издателей
`EIP · EPM · AVM`. Каждый проект ставит его у себя действием `family-badge`;
как читать цвета — в [контракте](export/README.md).

Собирается прогоном из ответов самих проектов, а не нашей оценки их: строка на
проект, число правил на каждый механизм, «родил» — сколько правил появилось у
проекта. Подробно, включая «кто уже решил то, что у соседа не держится
ничем», — [`export/where.md`](https://raw.githubusercontent.com/ArtVsMark/Engineering-Incidents-Playbook/badges/export/where.md).

**В этой сводке нет вас — и каталог об этом не узнает сам.** Правила берут без
спроса, они публичны; но обратную сторону — ваш ответ по каждому правилу и ваши
предложения — читать неоткуда, пока адрес не назван. Каталог наружу не пишет и
не ищет: сказать о себе может только сам проект,
[заявкой](https://github.com/ArtVsMark/Engineering-Incidents-Playbook/issues/new?template=consumer-announce.yml).
